## Why

OpsKeeper 对外已经是一个真实的 MCP server：`POST /api/v1/mcp` 走 JSON-RPC 2.0，带租户鉴权、
可选的 HMAC 完整性校验、按调用者身份过滤的工具可见性，每次 `tools/call` 写一条审计链并
回传 `X-Opskeeper-Audit-ID`（`docs/mcp-surface.md`）。这份契约是云厂商 Agent 接入平台的
唯一入口，但它至今只被两类东西碰过：

- **协议面测试**：`make mcp-surface-check` 用仓内自己的客户端打真 handler，钉住握手、保活、
  分页、可见性九条，外加一条晚接线陷阱测试。它证明的是「协议是对的」。
- **仓内 e2e**：`tests/e2e/testenv` 默认全 fakes、零外部凭据，另有 live 与 real-llm 两种
  模式。real-llm 测的是 OpsKeeper **内部**的 AI——平台自己的 Agent 能不能把事办成。

两件事都没做过：**一个外部 Agent 像真实客户那样，只凭 `tools/list` 给它的东西和
`initialize` 里的 `instructions`，能不能把产品用明白、在哪里会卡住。**这是契约面唯一还没
被检验的性质，而它恰恰是这份契约存在的理由。

另一半理由是产能。`docs/test/e2e-catalog.md` 列了 105 条目标用例，清单自标记已落地 11 条
（`tests/e2e/` 实有 27 个测试文件，标记滞后于实现，但缺口量级不变）。逐条靠人写，编写
速度就是覆盖率的上限。

## What Changes

- 新增一条**探索通道**：一条 make 目标拉起带 fakes 的一次性 manager，铸造仅回环可用的限权
  测试令牌，输出测试章程与连接信息；任何外部 AI 用标准 MCP 客户端接入。仓内不绑定任何
  具体模型或 Agent 框架——接入方只要有 MCP 客户端。
- 新增**确定性判决层**：以 manager 侧审计链与调用轨迹为证据，断言不变量——每次调用都带
  audit id；`tools/list` 看不见的工具调不动；写与破坏类调用必进审批队列；租户不越界；
  无 5xx；应答不含凭据形状。**AI 的判断只记为线索，不作门禁。**
- 新增**固化通道**：一条失败轨迹可回放为脚本化的仓内客户端用例，并入 e2e 套件成为回归。
  探索发现的东西只有固化下来才算留下。
- 通道定位为**夜间或手动**运行，不进必过门禁。

## Non-goals

- 不让 AI 当裁判。非确定性的判决会训练出「trust me」，这是决策 119 在 deadcode 上
  已经写过的教训：工具故意不做成闸门，因为会误报的闸门教人跳过它。
- 不扩大 MCP 工具面。本 change 不新增工具、不放宽可见性；探索若暴露契约缺陷，另立 change。
- 不对生产或预发环境开放。令牌只对 testenv 进程有效。
- 不替换现有套件。确定性 e2e 仍是回归的底座，探索通道是它的上游。

## Capabilities

### New Capabilities

- `mcp-ai-exploration-harness`: 一次性环境、测试令牌铸造、章程分发、轨迹采集、不变量判决
  与回放固化——外部 AI 经 MCP 契约验证 OpsKeeper 的可重复通道。

### Modified Capabilities

- None。本 change 不改 `docs/mcp-surface.md` 承诺的任何行为。

## Impact

- 新增测试代码与一条 make 目标；新增章程文档与探索报告的落盘格式。
- testenv 需要暴露两个测试专用的读口：令牌铸造，以及按会话导出审计行。仅测试构建可见，
  生产二进制零行为变更。
- 每次运行消耗接入方的模型额度，章程必须自带预算（工具调用数与步数上限），否则一次
  跑飞的探索就是一张账单。
- 回放用例进入 e2e 套件后受现有闸门约束（目录归属、构建标签覆盖、catalog 同步）。

## 待决问题（设计必须逐条回答）

1. **章程格式**：Markdown 清单还是结构化 YAML？与 `docs/test/e2e-catalog.md` 的「实现」列
   如何互认——一条用例被 AI 探索通过，算不算「实现」？（倾向：不算，只有回放固化后才勾。）
2. **轨迹采集点**：只靠 manager 侧审计链够不够？客户端侧是否需要 recorder 来补上
   「AI 看到了什么才做下一步」这一半。
3. **回放格式**：一条轨迹序列化成什么，仓内客户端用什么接口重放，重放结果如何与首次
   探索对账。
4. **令牌铸造的信任边界**：testenv 进程内签发，还是独立签发器；如何从结构上保证它签不出
   能打非 testenv 端点的凭据。
5. **报告落在哪、谁读**：探索报告是进 gatereport，还是独立产物；线索（AI 记的疑似问题）
   与判决（不变量断言结果）在报告里如何分开呈现。
