## Context

`chat-conversation` 现有 requirement「DeliverableCard 交付物卡」规定:对话流识别 serve_page / reports / pages 产出的链接,以「图标 + 标题 + 摘要 + 打开」渲染,**点击在新窗口打开产物**。

当前实现(`web/src/components/DeliverableCard.tsx`,41 行)与该约定一致但很薄:

- 白名单只有两条正则——`PAGE_RE = /^\/pages\/(\d+)(\/view)?$/`(`:9`)与 `REPORT_RE = /^\/reports\/(\d+)$/`(`:10`),由 `matchDeliverable`(`:14`)匹配;
- 渲染只有图标 + `label #id` + href 文本 + 一个 `window.open(info.href, '_blank')` 的按钮(`:36`);
- 唯一换卡点是 `MessageBubble.tsx:142-143`——markdown 链接命中即换卡。

结果是用户无法在对话里判断「这个产物是什么」,必须跳走,而跳走就丢了对话上下文。

**关键既有能力(可直接复用,不必重写)**:

| 能力 | 位置 | 备注 |
|---|---|---|
| 托管页缩略 | `Pages.tsx` `PageThumb`(`:44`) | 拉 HTML(bearer)→ `sandbox=""` 的 `srcdoc` iframe → 按 `THUMB_W=1100`(`:19`)缩放,`ResizeObserver`(`:51-52`)跟随宽度 |
| 托管页全尺寸预览 | `Pages.tsx:383` | 同样是 sandboxed srcdoc iframe |
| 报表内容渲染 | `ReportContentView`(`ReportContent.tsx:203`) | 渲染结构化 `ReportContentT`;`ReportDetail.tsx:128` 使用 |

**关键约束**:报表产物**不是** markdown 也**不是** HTML 页面,而是结构化 ContentJSON,由 `ReportContentView` 在 React 里渲染。因此报表**没有**可供 iframe 抓取的独立页面,无法做真实缩略图——除非引入服务端截图服务,而本 change 明确不引入后端改动。

## Goals / Non-Goals

**Goals:**

- 交付物卡带缩略,让「这是什么」在对话内一眼可辨。
- 点击卡片在**对话内就地预览**,不跳走、不丢失上下文。
- 聊天内预览与产物独立页面**共用同一套渲染逻辑**,不产生第二套渲染实现。
- 预览失败可优雅降级,用户始终保有「在新窗口打开」的出口。
- 识别面为白名单制,未列举的链接类型一律回退普通链接。

**Non-Goals:**

- 不新增任何后端 API,不上服务端截图服务。
- 不新增 npm 依赖。
- 不改动产物页(`Pages` / `ReportDetail`)自身的功能与布局。
- 不做跨源 iframe:缩略与预览仅限本应用同源托管页。
- 不为 postmortem / 工作流产物扩充识别面——其前端路由是否存在尚未证实(见 Open Questions),确认前白名单保持两条。

## Decisions

### D1 · 缩略复用 `PageThumb`,不新建缩略机制

**选择**:把 `Pages.tsx` 的 `PageThumb` 抽为共享组件,交付物卡直接消费。

**理由**:拉 HTML + sandbox iframe srcdoc + `ResizeObserver` 缩放这套逻辑已经写好且已在 `Pages.tsx:301` 投入使用。新写一套只会产生两个行为可能不一致的缩略实现,而缩略正确性直接关系到 iframe 安全边界——这类逻辑**越少越好**。

**备选与否决理由**:(a) 交付物卡内重写缩略——重复实现 iframe 加载与缩放,安全面翻倍;(b) 用 `<img>` 截图占位——没有截图服务,只能造假图,与「不伪造」的诚实原则冲突。

### D2 · 报表用类型化占位缩略,拒绝伪造截图

**选择**:报表卡渲染「图标 + 产物类型 + 生成时间」的占位缩略,**不做**任何形式的模拟截图。

**理由**:报表是结构化 ContentJSON,没有可供抓取的独立渲染页面。在没有服务端截图能力的前提下,任何「看起来像报表」的画面都是编造的——而本产品的核心主张恰恰是**防幻觉**(数字与状态必须有来源)。用一个假缩略骗过用户,是在产品最该诚实的地方撒谎。

**备选与否决理由**:(a) 把 ContentJSON 转成 HTML 再塞 iframe——需要一套转换逻辑,复杂度与失真风险都高于其价值;(b) 用纯图标不配任何信息——过于单薄,占位缩略至少传达「类型 + 时间」这一真实元数据。

### D3 · 预览在对话内就地展开,而非右侧抽屉

**选择**:点击卡片在消息流内展开预览区,占位在卡片自身下方。

**理由**:本 change 的价值主张是**不丢失对话上下文**。右侧抽屉虽然更宽敞,但它是一个新的浮层,用户视线仍需在对话与浮层间来回切换,且引入一层模态语义——而预览的本质是「看一眼这个产物长什么样」,是轻量、临时、局部的行为。就地展开更贴合这个语义,也更省实现复杂度。

**备选与否决理由**:右侧抽屉更适合长文档阅读。如果后续发现报表类长内容在就地展开下体验不佳(内容过高挤压消息流),可作为演进项再引入抽屉——但首个版本不做,以最小改动验证核心假设。

### D4 · 抽取共享只读渲染器,聊天预览与独立页面共用

**选择**:托管页预览与报表预览各自从现有页面抽出**纯展示子组件**,由交付物卡与原页面共同消费。

**理由**:若交付物卡自己写一套预览 UI,同一产物在两个地方会有两种渲染表现——托管页在 `Pages` 页显示一种样子、在对话里显示另一种,这是用户可感知的不一致,也让后续 bug 修复要改两处。

**备选与否决理由**:直接复用整个页面组件不可行——`PageThumb` 与报表页都自带数据获取逻辑,直接复用会把取数耦合进对话流渲染。抽取时要保证新组件是**纯展示**的:props 只收内容,数据获取留在调用方。若抽取过程中发现既有页面组件与取数耦合过深,则退一步只抽展示层、保留各自的数据获取,不在本 change 内做大规模解耦。

### D5 · 识别面白名单制

**选择**:只有显式列举路由的正则才升级为交付物卡;任何不匹配的链接回退为普通 `<a>`。

**理由**:这是既有 spec 已确立的原则(「无法识别的链接 MUST 回退为普通链接」),本 change 继续强化它。识别面一旦放宽,误匹配的普通链接会被静默变成一张无意义的卡——这是比「没识别出来」更糟的失败模式。

### D6 · iframe 安全边界

**选择**:所有 `srcdoc` iframe 强制 `sandbox=""`(不允许脚本、不允许同源、不允许表单与弹窗),且只渲染本应用同源的托管页 HTML。

**理由**:托管页 HTML 由 Agent 生成,内容不完全可信。`sandbox=""` 是全属性收紧的空值沙箱,与 `Pages.tsx:72`、`:383` 的既有写法一致——本 change 复用该模式,不引入更宽松的沙箱配置。

### D7 · 缩略懒挂载并限量

**选择**:缩略懒挂载(进入视口或卡片可见时再加载),单条消息内缩略数量设上限。

**理由**:一条长对话可能包含多个交付物,每个缩略都是一个加载 HTML + 建 iframe 的完整渲染。若无节制地同时挂载,滚动会明显卡顿。这是本 change 唯一的真实性能风险点。

## Risks / Trade-offs

- **[iframe 安全被无意放宽]** → 强制 `sandbox=""` 与同源白名单;代码审查显式检查 `sandbox` 属性存在且为空值,不允许出现 `allow-scripts` 之类放宽配置。
- **[多条消息缩略同时加载导致滚动卡顿]** → 懒挂载 + 单条消息缩略数量上限;缩略 iframe 高度固定,避免布局抖动。
- **[抽取渲染器时被迫大改既有页面组件]** → 抽取限定为纯展示子组件;若发现既有组件与数据获取耦合过深,退一步只抽展示层并保留各自取数,不在本 change 内做大规模解耦(见 D4 备选)。
- **[就地展开使长报表挤压消息流]** → 已接受的首个版本风险;报表预览设最大高度并内部滚动,不撑开消息流。若实测不可接受,后续演进为抽屉(见 D3)。
- **[白名单过窄导致部分产物仍是「跳走」体验]** → 有意为之。未证实路由的产物保持原行为,不引入「看起来对但其实是占位」的半吊子卡片。
- **[缩略失败与产物消失混淆]** → 三态显式区分 `loading / ready / failed`;`failed` 态保留「新窗口打开」出口,不让用户彻底失去访问路径。

## Migration Plan

纯前端增量改造,无数据迁移、无 API 变更、无配置开关。回滚策略是还原 `DeliverableCard.tsx` 的点击行为至 `window.open`,并移除缩略窗格——改动集中在该组件及其新增的共享子组件,不触碰产物页的数据获取路径。

## Open Questions

- **Q7**:是否存在稳定的 postmortem / 工作流产物**前端路由**,可供识别面扩展?若存在,白名单可增加对应条目并复用同一套渲染器;若不存在,本 change 的识别面保持 `/pages`、`/reports` 两条。此问题在 design 阶段核查路由表后定案。
- 报表预览在就地展开下的最大高度取值,需在 design 阶段结合实际报表长度分布确定。
