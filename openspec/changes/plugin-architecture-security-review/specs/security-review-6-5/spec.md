## ADDED Requirements

### Requirement: 八项安全审查每项都有一手证据或登记缺口

§6.5 的八个条目（secret 管理、日志脱敏、越权、跨租户、prompt injection、审批绕过、审计缺失、网络出口）中，每一项 MUST 要么指向至少一条在基线 commit 上可复跑的闸门或测试作为「已覆盖」证据，要么登记为缺口并给出整改建议；MUST NOT 出现既无证据又未登记缺口的条目。

#### Scenario: 条目有既有防线

- **WHEN** 某条目在仓内已有防线（代码 + 测试/闸门）
- **THEN** 审查报告引用具体文件路径与测试函数名，且该引用在基线 commit 上存在

#### Scenario: 条目无防线或防线不全

- **WHEN** 某条目存在未被覆盖的面
- **THEN** 报告登记缺口并分「正式版阻塞」或「后续版本」两档，附整改建议

### Requirement: 缺口分档标准固定

缺口的分档 MUST 以「当前生产默认配置下是否成立」与「影响面是否为凭据泄露、越权执行或跨租户数据外泄」为唯一标准；需要管理员主动配错才触发的缺口 MUST NOT 登记为正式版阻塞。

#### Scenario: 生产默认即成立的凭据/越权缺口

- **WHEN** 缺口在生产部署默认配置下成立且影响凭据或越权
- **THEN** 登记为正式版阻塞（S 级）

#### Scenario: 需错误配置才触发的缺口

- **WHEN** 缺口仅在管理员显式配置错误时成立
- **THEN** 登记为后续版本（F 级）并写明触发前提

### Requirement: 审查证据必须一手

报告引用的每个测试结论 MUST 来自在基线 commit 干净检出上的本次复跑或源码重读；MUST NOT 引用历史 PR 描述或他人转述的测试结论。

#### Scenario: 引用测试证据

- **WHEN** 报告声称某测试覆盖某防线
- **THEN** 该测试函数在基线 commit 存在，且报告给出包路径与函数名可 `-run` 精确命中

#### Scenario: 引用闸门证据

- **WHEN** 报告声称某闸门通过
- **THEN** 闸门命令在基线 commit 干净检出上执行且退出码为 0，命令原文记录在报告 §0
