## Context

任务书点名了要盘点的既有防线：audit_open_source、redaction 测试、promptguard、审批双签、sandbox 四禁、tool gateway 七闸（#139 刚落地）、跨租户 tenantkey 推导闸门。审查方法是先把这些防线全部定位到具体文件与测试，再按 6.5 的八个条目归位，最后对每个条目问两个问题：这条防线的证据是可复跑的吗？这条防线之外还有什么没被它覆盖？

所有测试在 `main@f4b76a36` 干净检出上复跑（见报告 §0 的命令清单与结果），不引用 CI 或他人转述。

## 候选方案

**A. 逐项审查 + 缺口分档（采用）。** 八个条目各自独立成节，每节先列已覆盖证据再列缺口；缺口按「正式版阻塞 / 后续版本」分档。理由：任务书要求的就是这个形态——「每项给出已覆盖的闸门/测试证据或缺口与整改建议」，且缺口必须区分两档。

**B. 按防线组织而非按条目组织。** 拒绝。那样每个防线写一遍，但「哪个 6.5 条目没有防线」要读者自己推，收口就成了拼图游戏。

**C. 只报缺口不盘点已有防线。** 拒绝。任务书明确要求「仓内既有防线先盘点再补缺」——不盘点就无法判断一个缺口是真缺口还是已有防线只是没被对上号。

## 取舍与采用

采用 A。两个具体裁决：

1. **缺口的归责口径。** 一个缺口被登记为「正式版阻塞」的唯一标准是：它在当前生产默认配置下就成立（不是需要错误配置才触发），且影响面是凭据泄露、越权执行或跨租户数据外泄。仅影响非默认路径、或需要管理员主动配错才触发的，归后续版本。
2. **证据的时效口径。** 每条证据都是本次在 `f4b76a36` 上复跑或重读的。报告不引用历史 PR 描述里的测试结论——那是二手读数，6.5 的性质是发布前收口，必须一手。

## 风险

- 报告本身可能过时：后续提交改掉任一被引用的测试名或文件，报告的引用就失效。缓解：每条证据给文件路径 + 测试函数名，便于 grep 复核；tasks 里把「复核」列为发布前动作而非一次性动作。
- 审查是快照不是过程：本次审过的面在下一个 PR 里可能引入新缺口。缓解：routeaudit、ledgercheck、plansecurity、audit_open_source 这些闸门本身就是把「审查发现」固化成可复跑检查的机制，报告的缺口章节里凡能固化成闸门的都建议了固化路径。

## 验证方式

- 报告 §0 列出的全部命令在干净检出上复跑并通过（本次已执行）。
- 每个引用的测试函数名在对应包里存在且以 `-run` 精确命中（本次已执行）。
