## Context

本 change 是 Phase 4 六方向中唯一的**远期后端立项**:本 Phase 4 内只给定形态与分期,不实现。可复用地基:事件群聊形态(会话共享的直接参照)、审批「谁可签」机制(排班联动点)、IM bridge(排班提醒)、zustand persist(第一层本地偏好)。

设计底线:记忆必须用户可见可删、不跨用户泄漏;排班只影响路由与提醒,不改双签约束。

## Goals / Non-Goals

**Goals:**
- 三层形态定界:第一层本地偏好持久化(前端可离线)→ 第二层用户级记忆(需后端)→ 第三层会话共享与 oncall 排班(需后端)
- 第二层优先于第三层的分期顺序
- 记忆透明可删的用户主权形态

**Non-Goals:**
- 本 Phase 4 内不实现,只立项定形态
- 不做多租户重建(org 域已裁)
- 记忆必须用户可见可删,不跨用户泄漏
- 排班只影响路由与提醒,不改双签约束

## Decisions

- **D1 三层分期**:第一层(偏好持久化)零后端、可立即做;第二层(用户级记忆存储+会话注入)是核心价值,优先于第三层;第三层(会话共享/排班)依赖第二层的用户身份,排后。每层独立可验收。
- **D2 记忆形态=偏好+事实+习惯**:结构化条目而非自由文本库;每条带来源与时间;会话开始时注入 Agent 系统提示词。
- **D3 用户主权**:前端提供记忆查看/编辑/删除入口;记忆不跨用户泄漏;Agent 使用记忆时可在上下文面板(见 D3 方向 session-context-panel)溯源。
- **D4 共享复用事件群聊**:会话共享直接复用既有事件群聊形态(成员/消息流/审批卡),不建新协作模型。
- **D5 排班只改路由不改治理**:oncall 排班决定告警路由与提醒对象、审批「谁可签」的候选人范围;双签数量与约束不变。

## Risks / Trade-offs

- [org/多租户边界未定(Q6)影响排班与共享范围] → Q6 单独立项论证;本形态按「单组织内团队协作」定界,不预设多租户
- [记忆注入造成行为漂移或泄漏] → 注入条目白名单化(结构化偏好/事实),透明可删,可溯源
- [排班与审批联动误改治理边界] → D5 硬约束:排班仅影响候选人与提醒,双签机制不动

## Migration Plan

分期立项:第一层可随 Phase 4 后续实现;第二、三层各自独立立项实现。无本期内数据迁移。
